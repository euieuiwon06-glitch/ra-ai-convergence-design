# G-1 컨셉 고도화 — 청중 반응 시뮬레이션 & 벤치마크 비교 (타겟 재정의판)

이 문서는 `G1_발표습관코칭_기획총정리_코드작업지시서.md`(프로토타입 스펙)의 후속 기획 문서. 기존 프로토타입을 갈아엎는 게 아니라, 포지셔닝을 "자세 교정 툴"에서 **"발표의 설득력을 분석해주는 코치"**로 격상시키기 위한 컨셉 재정의 + 두 신규 기능(청중 반응 시뮬레이션, 벤치마크 비교) 스펙을 정리한다.

---

## 0. 반려 배경 및 이번 개정의 방향

> **1차 초안 반려 사유**: "컨셉이 07/08 리포트 화면 2개에 기능을 얹은 수준에 그침. 타겟이 '발표하는 사람 누구나'로 막연해서 왜 이 기능이 절실한지 설득력이 없음."

1차 초안은 "청중 반응 시뮬레이션"이라는 기능을 먼저 정하고 나서 그걸 붙일 화면(07, 08번)을 찾는 순서로 짜여 있었다. 그러다 보니 리포트 화면에 카드 2개, 그래프 트랙 1개가 추가되는 수준에서 기획이 끝나버렸고, "왜 하필 청중 반응이고 왜 하필 벤치마크인가"에 답을 주는 타겟이 없었다.

이번 개정은 순서를 뒤집는다.

```
타겟 좁히기 → 그 타겟의 언어로 한 문장 컨셉 못박기 → 앱 전체 카피(스플래시~CTA)를
그 문장에서 파생시키기 → 마지막에 두 기능을 그 컨셉의 증거로 배치하기
```

UI 리디자인·컬러/타이포 시스템 확정은 여전히 다음 단계다. 이번 문서는 카피·문구·구조 레벨의 기획까지만 다룬다.

## 1. 타겟 리서치 — 3개 후보 비교

"발표하는 사람"을 다시 세 개의 구체적 후보로 쪼개 각각의 커뮤니티 반응과 관련 서비스 소구점을 리서치했다.

| 후보 | 커뮤니티/서비스에서 확인된 핵심 불안 | 관련 서비스 소구점 | 앱 메커니즘과의 적합도 |
|---|---|---|---|
| ① 취업 면접 준비생 (PT면접) | "면접관은 내용만큼 태도를 본다"는 지적이 반복됨. 블라인드에는 "PT면접 한번도 해본 적 없다"는 실전 경험 부재 불안, "PT발표에서 잘하는 것처럼 보이는 팁" 등 인상관리 노하우 공유 글이 다수. AI 자소서 확산 이후 PT·토론면접 비중이 커지는 채용 트렌드도 확인됨 | 사람인 AI모의면접·원티드 AI면접코칭은 답변 내용·꼬리질문 매칭이 중심. 해외 Yoodli는 "eye contact가 화상면접에서 인지된 자신감과 상관관계가 있다"며 이미 자세/시선을 소구점으로 쓰지만, 한국어 서비스엔 이 지점이 비어 있음 | **매우 높음** — 면접은 "평가자가 보고 있다"는 전제가 명확하고, PT면접은 정해진 시간 발표 자료를 발표하는 형식이라 이 앱의 녹화·자세감지 세션 구조와 그대로 겹침 |
| ② 발표대회·과제 PT 준비 대학생 | 발표불안 관련 상담 글, 심사위원 앞 공모전 PT에서 "근거(설득력)가 차이를 만든다"는 팁 확인 | 대학 교수학습지원센터의 "발표 공포증 극복법" 콘텐츠 정도. 상업 서비스는 거의 없음 | 중간 — 불안은 실재하지만 "합격/불합격"처럼 이분법적 결과가 없어 절박함이 ①보다 약함. 상당수가 ①(취준생)과 인구가 겹침 |
| ③ 사내 프레젠터 | "발표 시간이 다가오면 머리가 하얘지고 목소리가 떨린다"는 스피치학원 후기 다수. 리멤버·블라인드에 스피치학원 후기 존재 | 라온제나·플러스스피치 등 오프라인 스피치학원이 촬영+전문가 피드백으로 이미 시장을 점유. "3회 이내 안 바뀌면 환불" 등 결과 보증형 마케팅 | 낮음 — 값비싼 오프라인 코칭이 이미 자리잡은 시장이라 웹캠 앱 하나로 대체 가치를 주장하기 어렵고, 학생 신분으로 이 타겟에 리서치 접근하기도 어려움 |

## 2. 최종 타겟 선정

> **선정: "PT면접(발표형 면접)을 앞둔 취업준비생"**

**왜 ②가 아닌가**: 발표대회 준비생의 불안도 실재하지만 "합격/불합격"이라는 명확한 이해관계가 없어 "내가 청중에게 어떻게 보였는가"를 확인하려는 절박함이 ①보다 약하다. 게다가 PT면접 준비생 상당수가 이미 대학생이라 ②의 핵심 인구를 상당 부분 포함한다.

**왜 ③이 아닌가**: 사내 발표 불안은 실재하지만, 이 세그먼트는 이미 값비싼 오프라인 스피치 학원(촬영+전문가 피드백)이 시장을 점유하고 있어 학생이 만든 웹캠 프로토타입이 대체 가치를 주장하기 어렵다. 학생 신분으로 이 타겟에 리서치 접근하기도 어렵다.

**PT면접으로 좁히는 핵심 논거**: 인성면접·실무면접 같은 대화형 면접은 "웹캠 앞에 서서 발표하는" 이 앱의 세션 구조와 잘 맞지 않는다. 반면 PT면접은 실제로 "정해진 시간 동안 발표 자료를 발표하는" 형식이라 이 앱의 녹화·자세감지 메커니즘과 1:1로 대응한다. 게다가 PT면접은 기업 공식 평가 기준에 "발표태도·커뮤니케이션"이 명시되어 있어(링커리어 PT면접 평가기준 자료), "자세가 평가받는다"는 전제가 다른 어떤 발표 상황보다 명확하다.

## 3. 한 문장 컨셉

> **"이 앱은 PT면접을 앞둔 취업준비생이 면접관 앞에 서기 전 마지막 리허설에서, 내 발표가 면접관에게 실제로 설득력 있게 전달되고 있는지를 확인하게 해주는 앱이다."**

이후 모든 화면·카피·기능은 이 문장에서 파생된다. 문장 안의 세 키워드가 각각 다른 설계 결정으로 이어진다.

| 키워드 | 파생 결정 |
|---|---|
| **마지막 리허설** | 온보딩·홈 화면의 시점 설정(=지금은 연습이 아니라 실전 직전이라는 톤) |
| **면접관에게** | "청중"이라는 막연한 대상이 "면접관"이라는 구체적 인물로 좁혀짐 → 기능① |
| **설득력 있게 전달되고 있는지 확인** | "확인"이라는 동사를 시각화 기능으로 번역 → 기능② |

## 4. 앱 전체 카피 확장

컨셉이 리포트 화면에만 머물지 않도록, 스플래시부터 CTA 버튼까지 전 화면 카피를 리라이트한다. (실제 UI 레이아웃/색상 변경은 다음 단계, 여기선 문구 레벨 제안까지만.)

### 4-1. 태그라인 (앱 전체를 관통하는 슬로건)

| 안 | 문구 | 비고 |
|---|---|---|
| **추천** | **"내용은 준비됐다, 이제 태도를 준비할 차례."** | 앱 이름 Poise(침착함·태도)와 의미가 직결됨. "면접관은 내용만큼 태도를 본다"는 리서치 근거와 바로 연결됨 |
| 대안 A | "면접관이 보는 나를, 면접 전에 먼저 만나다" | |
| 대안 B | "떨림은 못 없애도, 안 보이게는 할 수 있다" | 톤이 더 직설적 — 다음 단계 리디자인 시 재검토 |

### 4-2. 스플래시(01)

- 기존: `발표 습관을 다듬는 AI 연습 코치`
- 제안: `면접관 앞에 서기 전, 마지막 리허설`

### 4-3. 온보딩(02) — 흐름 확장

현재 온보딩은 "폰을 세로로 세우고 1m 거리에서 촬영하세요"라는 순수 기능 안내 1장뿐이다. 그 앞에 타겟의 불안을 짚는 문제 제기 카드를 1장 추가할 것을 제안한다.

| 순서 | 화면 | 카피(안) |
|---|---|---|
| 02-a (신규) | 문제 제기 | H1: "답변은 준비됐는데, 어떻게 전달되는지는 본 적 없으시죠?" / 서브: "PT면접에서 면접관은 내용만큼 태도를 봅니다. 시선, 고개, 몸의 흔들림 — 스스로는 못 보는 습관을 Poise가 대신 지켜봐요." / CTA: "내 발표 확인하러 가기" |
| 02-b (기존 유지) | 촬영 가이드 | "폰을 세로로 세우고 1m 거리에서 촬영하세요" — 그대로 유지, 02-a 다음에 자연스럽게 이어짐 |

> 화면을 실제로 2장으로 나눌지, 한 화면 안에서 스와이프로 처리할지는 다음 단계(리디자인)에서 결정한다.

### 4-4. 홈(03) — 인사말 리라이트

- 기존(실제 코드 카피): `안녕하세요, 원의님` / `오늘도 발표 연습해볼까요?`
- **제안**: `원의님, 오늘은 면접관 앞이라고 생각하고 서볼까요?`
- 대안: `원의님, 이번 PT 리허설 시작해볼까요?` (PT면접 외 범용 발표에도 어색하지 않은 버전)

직전 세션 요약 카드는 레이아웃을 유지하되, 기능①이 반영되면 "면접관 몰입도 평균 OO점" 한 줄이 추가될 수 있다(6장 참고).

### 4-5. CTA 버튼 카피

| 위치 | 기존 | 제안 |
|---|---|---|
| 홈 하단 시작 버튼 | `연습 시작하기` | `리허설 시작하기` |
| 온보딩 시작 버튼 | `시작하기` | 그대로 유지 — 앱 첫 진입 시점엔 아직 타겟 맥락이 안 잡혀 있으므로 과한 카피는 지양 |
| 리포트 하단 | `다시 연습` / `통계 보기` | `다시 리허설` / `통계 보기`(유지) |

### 4-6. 리포트(07) 코치 코멘트 — 리라이트 원칙과 예시

- 기존: `시선 회피가 가장 잦았어요. 청중을 천천히 둘러보는 연습을 해봐요.`
- 제안: `시선 회피가 가장 잦았어요. 면접관은 이걸 '자신감 부족'으로 읽을 수 있어요 — 다음 리허설엔 3초씩 시선을 고정해봐요.`
- 기존: `시선을 천천히 옮기는 연습이 도움돼요. 청중을 3~4구역으로 나눠 바라보세요.`
- 제안: `면접관이 여러 명이라면, 3~4구역으로 나눠 순서대로 바라보는 연습이 도움돼요.`

> 원칙: 코치 코멘트 템플릿에 "면접관"이라는 단어와 그로 인한 "인상" 결과를 붙인다. 전체 문구 세트 확정은 다음 단계.

## 5. 기능 ↔ 타겟 연결 서사

> PT면접에서 가장 두려운 지점은 "내용은 논리적으로 준비했는데 왜 떨어졌는지 모르겠다"는 불확실성이다. 면접관은 포커페이스를 유지하고, 지원자는 발표 도중 실시간 반응을 전혀 읽을 수 없다. 즉 PT면접의 공포는 "평가 기준을 모른다"가 아니라 **"내가 지금 설득하고 있는지 아닌지 실시간으로 알 수 없다"**는 데서 온다.
>
> **면접관 몰입도 시뮬레이션**은 이 "보이지 않는 면접관의 반응"을 리허설 단계에서 대신 보여주는 장치다. **벤치마크 비교**는 PT면접이 본질적으로 상대평가(합격자 수가 정해진 경쟁)라는 점에서, "내가 지금 합격권 태도에 가까운가"를 확인하려는 스터디 문화(면접 스터디에서 서로 비교·피드백하는 관행)를 앱 안으로 옮긴 것이다.

두 기능은 "리포트에 얹은 부가 기능"이 아니라, 3장의 한 문장 컨셉이 요구하는 두 가지 확인(면접관에게 어떻게 보이는가 / 그게 충분한 수준인가)에 대한 직접적인 답이다.

## 6. 기능 재조정① — 면접관 몰입도 시뮬레이션 (구 "가상 청중 반응 시뮬레이션")

알고리즘은 1차 초안의 설계를 그대로 유지하고, 명칭·카피·화면 내 서사만 타겟에 맞게 재조정했다.

**입력 데이터**: 기존 `timeline`(클래스별 이벤트 타임스탬프 배열) + `duration_sec`. Supabase 스키마 변경 없이 렌더링 시점에 클라이언트에서 파생 계산한다.

**계산 로직 (의사코드 수준)**
- 세션을 5초 버킷으로 분할 (기존 1.5초 판정 윈도우와는 별개의 "집계 표시용" 스케일)
- 시작값 100(baseline)에서 버킷마다 해당 구간 이벤트에 가중 감점
  - 발화 멈춤 −10 (침묵이 청중 몰입을 가장 크게 깨는 신호)
  - 시선 회피 −8 (Yoodli가 eye contact를 핵심 지표로 다룰 만큼 비중이 큼)
  - 상체 흔들림 −6
  - 고개 움직임 −4
  - 한 버킷 내 중복 이벤트는 가중치 합산하되, 버킷당 최대 감점 −20으로 캡(급락 과장 방지)
- 정상 지속 버킷은 +3/버킷 회복(최대 100) — "집중력은 문제가 사라지면 서서히 돌아온다"는 설계 의도
- 3버킷 이동평균으로 스무딩 → 라인/에어리어 곡선

**화면 배치**

| 화면 | 반영 내용 |
|---|---|
| 07 세션 리포트·요약 | "이 리허설, 면접관을 얼마나 붙잡았을까요?" 카드 신규 — 평균 몰입도 점수 + 직전 회차 대비 증감(기존 "이번 회차에서 달라진 점" 패턴 재사용) + 최저점 구간 하이라이트("이 구간에서 면접관의 시선이 흔들렸을 수 있어요") |
| 08 세션 리포트·타임라인 | 기존 밀도 에어리어 그래프 바로 아래 새 트랙으로 몰입도 곡선 추가. X축은 기존 타임라인과 동기화. 저점(<50) 구간에 표정 아이콘 마커, 탭하면 기존 틱과 동일하게 해당 시점 영상으로 이동 |

**컬러/톤 원칙** (색상 자체 설계는 다음 단계 — 매핑 원칙만 명시): 새 색을 만들지 않고 기존 문법 재사용 — 고몰입=민트(#3FB27A) → 저몰입=경고 주황 그라디언트. 실시간 코칭 화면에서 이미 학습된 색 의미를 리포트에서도 연장한다.

## 7. 기능 재조정② — PT면접 태도 벤치마크 (레이더 차트)

**축 구성 (5개, 전부 "높을수록 좋음"으로 방향 통일)**

| 축 | 계산 |
|---|---|
| 시선 안정성 | `100 − min(100, (분당 시선회피 발생횟수 / 기준임계값) × 100)` |
| 고개 안정성 | 상동, 고개 움직임 기준 |
| 상체 안정성 | 상동, 상체 흔들림 기준 |
| 발화 유지력 | 상동, 발화 멈춤 기준 (실제 음성분석이 아닌 움직임 정지 프록시임을 라벨에 명시) |
| 면접관 몰입도 유지력 | 6장에서 계산한 평균 몰입도 점수를 그대로 재사용 — 두 기능이 하나의 데이터 파이프라인 위에서 동작한다는 설계 일관성을 보여줌 |

기준임계값은 "발표 코칭 통념적 임계값"의 근사치이며, 문서에 **"실사용 데이터가 쌓이면 사용자 집단 평균으로 대체 가능한 구조로 설계"**했음을 명시한다.

**비교 기준선**: "참고 기준선"이라는 표현으로 명확히 라벨링 — 실제 합격 데이터가 아니라 리서치 기반 추정치임을 라벨/툴팁에 고지한다(`"리서치 기반 참고 기준선이며 실제 합격 여부와는 무관해요"`). 세그먼트 토글로 "직전 회차" / "나의 최고 기록"과도 비교 가능(완전 pill 지양 원칙에 맞게 사각 세그먼트로). 사용자 폴리곤은 액센트(#5566FF) 채움, 비교 폴리곤은 점선 외곽선만.

**화면 배치**: 07번 세션 리포트·요약에 배치. 기존 도넛 차트(습관 분포의 "상대적 비중")와 역할이 다름을 구분한다 — 레이더는 "절대적 성과를 기준치/과거와 비교"하는 용도. 카드 카피: "면접 스터디에서 서로 비교하듯, 지난 리허설과 비교해봐요" — 실제 취준 커뮤니티의 스터디 상호 피드백 관행과 기능을 명시적으로 연결한다.

> 11번 기록·통계 화면에 축소된 레이더를 추가해 회차 간 트렌드로 확장하는 것은 향후 과제로만 언급, 이번 스펙 대상은 아님.

## 9. 데이터 모델 — 변경 범위와 이유

`supabase-setup.sql`의 `sessions` 테이블(`counts jsonb`, `timeline jsonb`, `duration_sec int`, `video_path`)을 기준으로:

- **기능①(몰입도 곡선)**: `timeline` 이벤트만으로 클라이언트에서 5초 버킷 감점/회복 곡선을 계산할 수 있음 → **스키마 변경 불필요**
- **기능②(벤치마크)**: `counts` + `duration_sec`으로 분당 발생빈도 정규화 가능 → **스키마 변경 불필요**. 참고 기준선 값은 하드코딩 상수(또는 별도 설정 JSON)로 관리
- 결론: 이번 컨셉 고도화는 **DB 스키마 변경 없이 클라이언트 계산 레이어만 추가**하는 것으로 충분하다.
